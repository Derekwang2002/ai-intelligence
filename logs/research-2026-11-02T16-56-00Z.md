### 1. OpenAI launches Grid Protectors; only the Georgia pilot has a finalized contract

**Recommended disposition:** `new-event` (WATCH; infrastructure/business-policy).  
**Official publication time:** `2026-11-02T15:00:00Z` in the OpenAI RSS feed, inside the strict window.  
**Canonical source:** https://openai.com/index/grid-protectors-program/  
**Corroborating utility sources:**

- https://www.georgiapower.com/news-hub/press-releases/georgia-power-to-serve-openai-project-in-effingham-county.html
- https://www.georgiapower.com/news-hub/press-releases/contract-openai-approved-part-portfolio-delivering-950-million-annual-savings.html

OpenAI announced a national program under which future compute campuses are intended to reduce load during grid stress and may supply power from on-site generation or storage. The program announcement is real, but most future-campus arrangements are not yet finalized; OpenAI says commitments will vary by location and be disclosed later.

The concrete pilot is the planned Effingham County, Georgia campus. Georgia Power says the approved 25-year agreement covers about 3,200 MW of new demand, requires OpenAI to pay the infrastructure and electric-service costs, and permits up to 1,000 MW of flexible demand response. The campus is still in development, so this is a signed/approved arrangement, not observed operational curtailment. Georgia Power's projected `$950 million/year` portfolio savings beginning in 2029 cover its broader large-load portfolio and expected growth; they must not be attributed solely to OpenAI or treated as realized savings.

**Why it changes a decision:** it turns data-center load flexibility from a general pledge into a named national program backed by one approved utility contract. It is still WATCH because the transferable operating evidence—actual curtailment duration, notice, workload impact, backup generation emissions, and realized ratepayer savings—does not exist yet.

### 3. NVIDIA documents Workload Map as a reusable Kubernetes workload translation layer

**Recommended disposition:** `update-existing`, event `ev-20261013-02`, if the editorial threshold treats newly documented production adoption as material; otherwise `filtered` with reason `documentation-of-existing-component`.  
**Official publication time:** `2026-11-02T16:00:00Z` in the NVIDIA developer feed.  
**Canonical sources:**

- https://developer.nvidia.com/blog/support-new-ai-frameworks-faster-using-nvidia-workload-map/
- https://github.com/dsx-ai-factory/workload-map
- https://github.com/dsx-ai-factory/workload-map/releases/tag/v0.3.0

NVIDIA published the first detailed engineering account of Workload Map, an Apache-2.0 CRD plus Go library that maps heterogeneous Kubernetes AI workload CRDs into a common tree. Its catalog includes JobSet, PyTorchJob, Ray, KServe, Knative, MPIJob, NIM, LeaderWorkerSet, Milvus, Grove and Dynamo. NVIDIA says Run:ai uses it in production; KAI Scheduler uses definitions as a fallback for gang scheduling, and Elotl Nova uses it for multi-cluster placement.

The software is not newly created in this window: the repository dates to 2025 and the latest stable release, `v0.3.0`, was published `2026-10-21T10:32:36Z`. The new fact is the official architecture/adoption disclosure, not a same-day binary release. The repository had 87 stars and 23 forks when checked; those are discovery context, not evidence of broad adoption.

**Why it may change a decision:** the existing Run:ai event already names Workload Map but does not explain that one declarative definition is reused for inspection, mutation, gang scheduling and platform visibility. A one-day TRIAL can install the CLI, register one supported and one custom CRD in an isolated cluster, and compare reported replicas/resources/status with native objects. Keep the limitation that production-use evidence is vendor-reported.
