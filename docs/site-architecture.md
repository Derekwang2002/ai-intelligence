# site/ 技术文档：一个知识库是怎么变成网站的

> 这份文档解释 `site/` 目录下的静态网站：它解决什么问题、每个关键技术选择为什么这么做、付出了什么代价、将来往哪走。
> 面向的读者是"几个月后接手改这个站的自己"，所以尽量说人话，少用黑话，用到了就顺手解释。

---

## 1. 一句话总结

**网站是知识库的一面镜子**：`events/`、`daily/`、`trends/` 这些文件是唯一真相（source of truth），网站只负责把它们变成好看的页面；构建时先把数据"拍照"成一份 JSON 快照，再用 Astro 把快照渲染成纯静态 HTML，push 到 GitHub 后由 Actions 自动发布到 GitHub Pages。

这个定位决定了后面所有的技术选型。

## 2. 需求与约束

选型之前先看清约束，脱离约束谈"什么框架最好"都是空谈。

**来自项目的约束（不可妥协）：**

- 知识库文件是 AI agent 增量维护的，格式由 `AGENTS.md` 规定，**网站绝不能反向修改它们**——只能读。
- 项目哲学是"不引入数据库、保持文件简单"。网站不能破坏这一点。
- 数据量很小且增长缓慢：目前每天新增 0~10 个事件，一年也就千级别。任何为"大数据量"做的设计都是过度设计。

**来自使用者的需求：**

- 目标是**阅读和观察**，不是管理：看今天发生了什么（日报）、看某个事件的细节（事件页）、看"我现在该用什么"（雷达）、看方向性变化（趋势）。
- 需要 **light/dark 双主题**，可手动切换也跟随系统。
- 需要**公开访问 + 自动更新**：agent 扫描完 → 提交 → push，网站自动重新发布，中间不允许有手动步骤。

## 3. 总体架构

先看一张数据流图，理解"一次更新"从头到尾经历了什么：

```text
                    ┌─────────────────────────────────────────────┐
                    │  知识库（唯一真相，agent 增量写入）              │
                    │  events/*.json   daily/*.md                  │
                    │  trends/*.md     index/events.json           │
                    │  state.json                                   │
                    └──────────────────┬──────────────────────────┘
                                       │ 只读
                     site/scripts/prepare-data.mjs
                     （dev / build 前自动运行）
                                       │
                                       ▼
                    ┌─────────────────────────────────────────────┐
                    │  site/src/data/generated/  （构建产物，不入库） │
                    │  events.json     —— 摊平的事件数组             │
                    │  aggregates.json —— 分类/组织/标签/日期聚合     │
                    │  daily.json      —— 日报 HTML + 摘要          │
                    │  trends.json     —— 结构化趋势 + 历史快照 HTML  │
                    │  state.json      —— 最后扫描时间、观察清单       │
                    └──────────────────┬──────────────────────────┘
                                       │ import JSON
                     Astro 构建（本地 ~0.4s，27 页）
                                       │
                                       ▼
                    ┌─────────────────────────────────────────────┐
                    │  site/dist/  纯静态 HTML + 少量内联 JS          │
                    └──────────────────┬──────────────────────────┘
                                       │ git push 触发
                     .github/workflows/deploy-site.yml
                                       │
                                       ▼
              https://derekwang2002.github.io/ai-intelligence/
```

**一个关键设计：数据管线是单向的、构建期的。** `prepare-data.mjs` 是唯一接触知识库源文件的地方，所有"脏活"（字段摊平、markdown 渲染、趋势解析、统计聚合）都在这一步完成，下游的页面组件拿到的永远是干净的 JSON。这带来两个好处：

1. 页面组件很"傻"，不用关心源文件格式长什么样；
2. 想知道"网站上某个数字是怎么算出来的"，只需要看这一个脚本。

## 4. 技术选型逐项分析

### 4.1 为什么是"纯静态站"，而不是动态应用？

**可选方案**：① 静态生成（SSG）；② 带后端的动态站（Next.js SSR / 一个小 Fastify + 模板）；③ 单页应用 + 运行时 fetch JSON。

**选了 ①，理由：**

- 数据已经全部是本地文件，没有任何"运行时查询"的需求——不需要用户登录、不需要动态计算、数据更新频率是"每天几次"而不是"每秒几次"。静态站把这个事实利用到极致：**构建 = 部署的全部**。
- 免费托管、无服务器维护、无安全面（没有后端就没有漏洞）、访问速度快（纯 CDN 分发文件）。
- 和 GitHub Actions 天然契合：push → build → deploy，一行命令的流水线。

**代价：**

- 所有"动态"能力（筛选、搜索、tooltip）只能靠客户端 JS 实现，数据必须全部预打包或预渲染。
- 极端情况下（几千个事件）单页 HTML 会变大——但按当前增速，这个担心至少三五年后才成立。

### 4.2 为什么框架选 Astro？（而不是 Next.js / VitePress / …）

先说结论：**这是个"内容驱动 + 数据驱动混合"的站点，Astro 恰好是为这类站点设计的**。逐个对比：

| 方案 | 优点 | 没选的原因 |
|---|---|---|
| **Astro** ✅ | 内容优先；默认零 JS（页面默认是纯 HTML，需要交互再加）；markdown 和 JSON 都是一等公民；构建极快 | 需要学一个很小的模板语法（`.astro`）；复杂交互最终还是要引框架（目前用不到） |
| Next.js | 生态最大、什么都能做 | 对纯静态内容站来说过重：默认绑 React runtime，构建链复杂，杀鸡用牛刀 |
| VitePress | 文档站开箱即用、零配置 | 主题定制受限，"雷达图/趋势看板"这种自定义数据视图不是它的主场，很快就会跟它搏斗 |
| Nuxt Content | 和 Astro 定位类似的 Vue 版 | 无 Vue 偏好时没有额外收益，生态上 Astro 的 content 用例更多 |
| Quartz | 笔记/数字花园专用 | 面向笔记链接网络，结构化数据视图弱 |
| 纯 Vite 手写模板 | 最轻、零依赖 | 路由、布局、打包细节全要自己造，长期维护成本反而最高 |

**Astro 最贴合的两个特性：**

1. **默认零 JS**：构建产物就是 HTML + CSS，只有三个小地方用了客户端脚本（主题切换、事件筛选、雷达 tooltip），总共不到 200 行原生 JS。对一个"阅读型"站点，这是性能和简洁的双重胜利。
2. **Islands 架构的退路**：将来如果出现一个确实复杂的交互视图（比如 benchmark 对比表格），可以只在那个组件里引入 React/Vue/Svelte，其他页面保持零 JS。这个"按需付费"的演进路径很让人安心。

**代价：**

- `.astro` 模板语法有些自己的规矩，比如**组件递归必须用 `Astro.self`**（直接引用自己的文件名会报 `not defined`，这是个真实的坑，本文档写作时已经踩过）。
- 相比 Next.js，社区里"现成的高级组件"少一些，很多东西（比如雷达图）要自己写——但对本项目来说自己写反而更可控。

### 4.3 依赖为什么只有 `astro` + `marked` 两个？

刻意保持的克制。每加一个依赖都是一条长期维护承诺（升级、安全、和 Astro 的兼容矩阵）。目前清单：

- `astro` — 框架本体（顺带包含 Vite 构建链）；
- `marked` — 把日报/趋势的 markdown 渲染成 HTML，成熟、零配置、够用。

**没有引入**的常见候选及原因：

- **图表库（ECharts / D3 / Chart.js）** → 见 4.6，雷达图手写 SVG。
- **CSS 框架（Tailwind 等）** → 站点只有一个全局样式文件 `global.css`，CSS 变量体系已经足够干净，引 Tailwind 反而多一层构建配置和抽象。
- **搜索（Pagefind / fuse.js）** → 当前 16 个事件，纯客户端过滤绰绰有余；等数据量真上来再加（见 §6）。
- **TypeScript 严格模式 / zod** → 数据来自自己写的管线，格式可控；上严格校验的收益目前小于成本（演进方向里保留了这一项）。

### 4.4 数据层：为什么先跑 `prepare-data.mjs`，而不是让页面直接读源文件？

理论上 Astro 页面可以直接 `import '../../events/2026-08-14.json'`，甚至用 Content Collections 的 glob loader 指向 `site/` 外面的目录。没这么做，原因按重要性排序：

1. **关注点分离**：知识库格式是给 agent 定的（`AGENTS.md`），不应该泄漏到 UI 代码里。`published_at` 有的是完整时间戳、有的只有日期；`update_2026_08_15` 这种字段名是动态的……这些"不规则"都在管线里抹平，页面组件只消费规整的字段（如统一派生的 `published_date`）。
2. **跨目录引用的脆弱性**：Content Collection 指向项目外目录在本地和 CI 的路径解析上容易出幺蛾子。管线脚本用 `fs` 读绝对路径，行为在任何环境都一致。
3. **预处理需要家**：日报的"摘要提取"（找到 `## Daily Executive Summary` 段落拿第一条 bullet）、`trends/current.md` 的结构化解析、组织/标签聚合统计，这些逻辑总得有个地方放，集中在管线里最清晰。

**代价：**

- dev server 运行中改了知识库文件，**不会自动重新跑管线**（`predev` 只在启动时跑一次）。需要手动 `node scripts/prepare-data.mjs` 再刷新。这是已知的体验瑕疵，写进了维护手册（§7.2）。
- 生成目录 `src/data/generated/` 被 gitignore，任何环境（包括 CI）都靠重新生成，好处是不会有"忘了同步生成文件"的脏状态。

### 4.5 Markdown 渲染：为什么是构建期 `marked`，而不是让浏览器渲染？

日报页的 HTML 是构建时就渲染好的（`prepare-data.mjs` 里调 `marked.parse`，存进 `daily.json`），浏览器拿到的是现成 HTML。替代方案——把 markdown 原文发给浏览器、前端渲染——会引入运行时依赖和闪烁，没有任何好处。

顺带做了两件小事：外部链接自动加 `target="_blank" rel="noopener"`；GFM 表格支持（日报里有表格）。

**代价：** `marked` 不做 sanitize。当前内容全部来自自己维护的知识库，风险可接受；如果将来渲染第三方内容，需要加 sanitize 步骤。

### 4.6 雷达图：为什么手写 SVG，而不是图表库？

这是最容易被质疑的一个选择，值得单独说清楚。

**需求本质**：ThoughtWorks 风格的"象限雷达"——4 个扇区 × 4 个同心环，每个事件是一个带编号的圆点。注意这**不是** ECharts 里的 "radar chart"（那是蜘蛛网图，完全不同的东西）。

**如果用图表库**：ECharts 没有现成的象限雷达类型，得用自定义系列硬拼；D3 可以做但要引 ~100KB+ 的库并且学它的数据连接那套 API。而我们需要的全部东西是：几个圆环、两条交叉轴线、一堆圆点 + tooltip。

**实际做法**：`RadarChart.astro` 在**构建期**生成整张 SVG（~100 行模板代码），圆点位置由事件 fingerprint 的确定性哈希计算——同一个 fingerprint 永远出现在同一位置，重建多少次布局都不变（这点很重要，否则每次部署用户会发现"图变了"）。tooltip 是页面上一段 30 行的原生 JS。

**优点**：零运行时依赖、构建期生成（首屏即出、无闪烁）、主题色直接用 CSS 变量（`fill: var(--adopt)`），深浅色切换零成本。

**代价**：圆点多了会重叠（哈希定位不做碰撞检测），交互升级（点击象限放大、拖拽）都得手写。按当前每个环最多十几个点的密度，没问题；这也是 §6 里"什么时候必须重写"的触发条件之一。

### 4.7 趋势数据：结构化 `current.json` 优先，markdown 解析为兜底

趋势数据由 agent 直接产出结构化的 `trends/current.json`（双语字段：`name_zh/en`、`evidence_zh/en`、`why_it_matters_zh/en`、`what_would_confirm_zh/en`、`updates[].note_zh/en`），`prepare-data.mjs` 优先消费它并规整成统一形状；`current.json` 缺失时回退到正则解析人读的 `trends/current.md`（识别 `### 状态: 名称` 标题和 `- **字段:**` 列表项）。

**为什么保留兜底**：格式由 `AGENTS.md` 约定，agent 一般会遵守，但漏写 `current.json` 或字段漂移时站点不应崩溃——回退路径用 md 解析结果填充同一套模板字段（英文填入 zh/en 两侧）。

**其余兜底**：

- 解析不到的字段显示为空，页面不会崩；
- 历史快照页（`/trends/archive/[date]/`）直接渲染 markdown HTML，完全不依赖解析。

**双语回退通则**：事件、日报、趋势快照都一样——某一语言缺失时回退到另一语言的内容，保证页面永远有内容（详见 §7.6）。

### 4.8 主题：CSS 变量 + `data-theme`，防闪烁的内联脚本

**方案**：所有颜色都是 CSS 变量，`:root` 定义浅色值，`[data-theme="dark"]` 覆盖深色值。`<html>` 元素上的 `data-theme` 属性决定用哪套。

三个细节各有理由：

1. **为什么不用纯 `@media (prefers-color-scheme)`**：那样用户无法手动切换——媒体查询是"只读"的。需求明确要手动切换 + 记忆偏好，所以必须 JS 控制 class/attribute。
2. **防闪烁（FOUC）**：主题判断脚本必须**内联在 `<head>` 里同步执行**（`<script is:inline>`），在浏览器画出第一帧之前就把 `data-theme` 设好。如果做成外部文件，用户会先看到默认色再闪一下切换——深色用户的体验灾难。
3. **优先级**：`localStorage` 里存的手动选择 > 系统偏好 > 默认深色。

**代价**：样式里用到了 `color-mix()`（需要 2023 年后的浏览器）；禁用 JS 的用户固定看到浅色主题。都属于可接受的现代基线。

### 4.9 部署：GitHub Pages + Actions，而不是 Vercel / Netlify / Cloudflare Pages

**为什么选 GitHub Pages：**

- 代码本来就在 GitHub，**不引入任何新账号、新服务、新授权**——"公开 + 自动更新"的需求零额外成本就满足了；
- Actions 的 `deploy-pages` 官方 action 把流程标准化了，workflow 一共 40 行；
- 免费、无额度焦虑（这个站的构建一分钟内）。

**诚实的缺点：**

- **没有 PR 预览**：Vercel/Netlify 会给每个 PR 一个临时 URL，改样式时很香；GitHub Pages 只能看 main。
- CDN 覆盖一般，部分地区访问速度不如 Cloudflare。

**为什么仍然接受**：这是个人项目、单人维护，PR 预览需求弱；而且因为站点是纯静态产物，**迁移成本接近零**——哪天想要 PR 预览了，把同一个仓库接到 Cloudflare Pages，改一行 base 配置就能跑。Astro 的官方适配让这种"随时可走"成为默认状态。

### 4.10 子路径问题：`ASTRO_BASE` 环境变量

GitHub Pages 的项目站部署在 `https://xxx.github.io/ai-intelligence/`（注意有 `/ai-intelligence` 前缀），而不是域名根。所有内部链接和资源引用都必须带上这个前缀，否则线上 404。

**方案**：

- `astro.config.mjs` 读 `ASTRO_BASE` 环境变量，本地默认 `/`（开发体验干净），CI 里传 `/ai-intelligence`；
- 页面代码里**禁止**手写 `/xxx` 链接，一律走 `src/lib/url.ts` 的 `u('/xxx')` 帮助函数。

**代价**：忘了用 `u()` 的链接本地正常、线上 404（这种 bug 最讨厌）。维护手册（§7.3）把它列为头号检查项。将来如果绑定自定义域名，改 workflow 里的一个环境变量就能去掉前缀。

## 5. 已知限制（诚实清单）

1. **dev 模式下改知识库不会自动刷新站点数据**——需手动重跑 `prepare-data.mjs`（§4.4）。
2. **趋势解析依赖 markdown 格式稳定**（§4.7），字段漂移会导致趋势页信息变少（不崩溃）。
3. **事件筛选是页面内客户端过滤**，事件数到几百个时仍然可用，到几千个就需要真正的索引（§6.1）。
4. **雷达图无碰撞检测**，单环几十个点时会重叠（§4.6）。
5. **没有 sitemap.xml 和 RSS**，订阅和 SEO 都还没做。
6. **日报摘要提取依赖 `## Daily Executive Summary` 这个标题**，改日报结构时要同步改正则。

## 6. 演进方向

按"什么信号出现就做什么"组织，避免为了演进而演进。

### 6.1 搜索：接 Pagefind（触发信号：事件数 > 300，或"找东西费劲"成为日常）

Pagefind 是专为静态站设计的搜索索引器：构建后跑一遍，为每个页面建倒排索引（每页只增加几 KB），浏览器端即装即用，支持中文。接入点已经在架构上留好——它是纯构建期工具，加一个 postbuild 步骤即可，不碰数据管线。

### 6.2 组织页 / 标签页（触发信号：想按公司看发布节奏）

`aggregates.json` 里已经算好了每个组织的事件列表和频率，加 `/orgs/[name]/` 页面是纯增量工作，半天以内。

### 6.3 趋势数据结构化（✅ 已在 v4 双语改造中落地）

`AGENTS.md` §10 已约定 agent 产出 `trends/current.json`（双语结构化），站点优先消费 JSON、保留 md 解析兜底（§4.7）。后续可在此基础上画"趋势状态随时间演变"的时间线图。

### 6.4 RSS + sitemap（触发信号：想被订阅/分享）

`@astrojs/rss` 和 `@astrojs/sitemap` 都是官方集成，各 10 分钟接入。RSS 对"增量情报"类内容价值特别高。

### 6.5 benchmark 对比视图（触发信号：想横向比较模型）

第一个"值得用 islands"的场景：一个可交互的对比表格（选两个事件，并排看 benchmark）。到时候在单个组件里引入轻量框架或继续手写都行——架构上没有障碍。

### 6.6 数据校验护栏（触发信号：知识库格式变更导致站点出过一次错）

给 `prepare-data.mjs` 加 zod schema：字段类型不对就构建失败（fail fast），而不是渲染出半空的页面。CI 是天然的执行点。

### 6.7 PR 预览 / CDN 升级（触发信号：多人协作，或国内访问慢成为实际抱怨）

接 Cloudflare Pages（同一仓库，自动 PR 预览，国内可达性好）。因为产物是纯静态目录，迁移是一行配置的事。

## 7. 维护手册

### 7.1 日常命令

```bash
cd site
npm install        # 首次
npm run dev        # 本地开发 → http://localhost:4321
npm run build      # 构建到 dist/（自动先跑数据管线）
ASTRO_BASE=/ai-intelligence npm run build   # 本地模拟线上构建，排查 404 用
```

### 7.2 常见任务

| 想做什么 | 去哪改 |
|---|---|
| 改颜色/字体/间距 | `src/styles/global.css`，只动 CSS 变量；**新增变量必须浅色深色成对出现** |
| 改 UI 文案（任一语言） | `src/lib/i18n.ts` 的 `ui` 字典；**zh / en 两个键集合必须保持一致** |
| 改雷达象限划分（哪个类别进哪个扇区） | `src/components/RadarChart.astro` 顶部的 `QUADRANTS` 数组 |
| 改类别显示名 | `src/lib/i18n.ts` 的 `CATEGORY_LABELS` |
| 改页面结构/样式 | `src/components/pages/` 下的共享模板（中英两套路由共用，改一处两语言同时生效） |
| 加新页面 | 共享模板放 `src/components/pages/`，再在 `src/pages/` 与 `src/pages/en/` 各加一个薄路由；动态路由的 `getStaticPaths` 写在薄路由里（参考 `events/[id].astro`） |
| 消费事件的新字段 | 不用改管线——管线透传整个事件对象，页面直接 `event.字段名`；双语文本字段用 `loc(event, 'summary', locale)` 取值 |
| 改部署仓库/域名 | workflow 里的 `ASTRO_BASE` + `astro.config.mjs` 的 `site` |

### 7.3 四个最容易踩的坑

1. **内链必须 `u('/path', locale)`**（`import { u } from '../lib/url'`）。手写 `/path` 或漏传 locale 在本地完全正常、线上 404 或串语言（中文页链到英文页）。
2. **组件递归必须 `Astro.self`**，不能在模板里引用自己的文件名。
3. **dev 运行中改了知识库**：手动跑 `node scripts/prepare-data.mjs` 再刷新浏览器，否则看到的还是旧数据。
4. **共享模板改结构只改 `src/components/pages/`**：`src/pages/` 和 `src/pages/en/` 下只是传 `locale` 的薄路由，不要在里面写页面逻辑。

### 7.4 页面路由一览

每个路由都有中英两份：中文在根路径，英文在 `/en/` 镜像路径（如 `/en/events/`）。下表只列中文路径：

| 路由 | 页面 | 数据来源 |
|---|---|---|
| `/` | 概览：今日简报执行摘要、最新事件、活跃趋势、建议分布 | 全部 |
| `/events/` | 事件时间线 + 筛选 | `events.json` + `aggregates.json` |
| `/events/[event_id]/` | 事件详情 | `events.json` |
| `/radar/` | 四象限技术雷达 | `events.json` |
| `/trends/` | 趋势看板 + 历史快照入口 | `trends.json` |
| `/trends/archive/[date]/` | 趋势快照原文 | `trends.json` |
| `/daily/` `/daily/[date]/` | 日报列表与阅读页 | `daily.json` |

### 7.6 双语机制（v4 起）

- **内容双语在知识库侧产出**（AGENTS.md §6/§7/§10）：事件 JSON 带 `summary_zh/en`、`why_it_matters_zh/en`；日报与趋势快照是 `YYYY-MM-DD.md` + `YYYY-MM-DD.en.md` 文件对；趋势看板是 `trends/current.json`（双语结构化）。站点只读，不做翻译。
- **管线**把文件对合成 `{ html_zh, html_en, excerpt_zh, excerpt_en }` 这类平铺字段；某一语言缺失时回退到另一语言，页面永不空白。
- **页面侧**用 `loc(obj, field, locale)` 取内容字段（`_zh` → `_en` → 原字段 的回退链），用 `t(locale, key)` 取 UI 文案（字典在 `src/lib/i18n.ts`）。
- **路由**：中文是默认语言无前缀，英文在 `/en/` 下；`u(path, locale)` 统一处理 base 前缀 + 语言前缀；`Base.astro` 头部的语言切换链接按当前路径计算对方语言 URL。
- **界面统一**：两种语言共用 `src/components/pages/` 里的同一套模板，不存在"英文版长得不一样"的可能。

### 7.5 评分与视觉的映射约定

- 六维评分（1–5）：技术影响 / 工程价值 / 采用信号 / 成熟度 / 验证成本 / 风险 → 详情页 `ScoreBars`，列表页只显示前三维的紧凑数字（`影响 4 · 工程 4 · 采用 3`）。
- 建议 → 颜色：ADOPT 绿 / TRIAL 蓝 / WATCH 琥珀 / IGNORE 灰，同时是雷达图从内到外的四个环。
- 类别不再有独立色相（v3 起移除 `--cat-*` 色系）：类别以纯文字标签显示，雷达象限用分区而非颜色区分。全站唯一强调色是深编辑蓝 `--accent`。
- v3 设计语言：编辑简报式（editorial briefing）——暖纸/暖墨双主题、serif 标题（`--serif`）、发丝线分隔、无渐变/发光/玻璃拟态。首页以最新日报的执行摘要为主角，站点遥测（观察清单、活动图）已从首页移除。
